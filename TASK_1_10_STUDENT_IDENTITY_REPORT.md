## Architecture Implemented

### Two-Entity Student Identity

**User Entity (Authentication Identity)**
- Primary Key: `id` (UUID, auto-generated)
- Represents: Authentication, account access, role-based permissions
- Used by: CV, SavedInternship, InternshipApplication, Recommendation, TeamMember, WeeklyLogbook, CampusLogistics, StudentActivityLog

**StudentProfile Entity (Academic Profile Identity)**
- Primary Key: `id` (BIGINT, auto-increment)
- Foreign Key: `user_id` (UUID, references User.id)
- Represents: Academic information, skills, interests, preferences
- Used by: StudentSkill, StudentInterest (join tables)

| Model | FK Field | FK Type | References | Rationale |
|-------|----------|---------|------------|-----------|
| StudentProfile | user_id | UUID | User.id | One-to-one relationship |
| StudentSkill | student_id | BIGINT | StudentProfile.id | Profile-specific data |

| CV | student_id | UUID | User.id | User-owned document |

## Code Review

### Why the unique constraint is necessary

**Problem:** Without a database-level unique constraint, multiple StudentProfile records could be created for the same User.id, violating the one-to-one relationship.

**Solution:** Adding `unique: true` to `StudentProfile.user_id` and an explicit index ensures PostgreSQL enforces uniqueness at the database level, preventing duplicate profiles for the same user.

**How Sequelize interprets the relationship:**
- `User.hasOne(StudentProfile, { foreignKey: 'user_id', as: 'profile' })` indicates one User can have one StudentProfile
- `StudentProfile.belongsTo(User, { foreignKey: 'user_id', as: 'user' })` indicates StudentProfile belongs to one User
- The unique constraint ensures this is enforced by the database, not just application logic

**How PostgreSQL enforces uniqueness:**
- PostgreSQL creates a B-tree index on `student_profiles_studentprofile.user_id`
- When inserting or updating, PostgreSQL checks if the value already exists
- If duplicate, PostgreSQL raises error code 23505 (unique_violation)
- Sequelize catches this as `SequelizeUniqueConstraintError`

### How User.id and StudentProfile.id work together

**User.id (UUID):**
- Generated by `DataTypes.UUIDV4` on User creation
- Used for authentication (JWT tokens reference this)
- Used for all user actions (applications, saved internships, team membership)
- Never changes, immutable identifier

**StudentProfile.id (BIGINT):**
- Auto-incremented integer, independent of User.id
- Used for profile-specific data (skills, interests via join tables)
- Provides a separate identity for academic profile operations
- Allows profile to be referenced without exposing User UUID in certain contexts

**Relationship:**
- StudentProfile.user_id links the two entities
- One User → One StudentProfile (enforced by unique constraint)
- User.id is the "public" identifier for most operations
- StudentProfile.id is the "internal" identifier for profile-specific joins

### Why TeamMember.student_id must be UUID

**TeamMember role:** Represents a User as a member of a ProjectTeam

**Association:**
```javascript
TeamMember.belongsTo(User, { foreignKey: 'student_id', as: 'studentUser', constraints: false });
```

**Application code usage:**
```javascript
// From projects.js
const member = await TeamMember.findOne({ where: { student_id: req.user.id } });
await TeamMember.findOrCreate({
  where: { team_id: team.id, student_id: req.user.id },
  // ...
});
```

**Why UUID is correct:**
- `req.user.id` is a UUID (from User model)
- TeamMember queries use `req.user.id` directly
- Association references User.id (UUID)
- Using BIGINT would cause type mismatch and query failures

**Preservation of uncommitted change:**
- The committed version had BIGINT (incorrect)
- The uncommitted version changed to UUID (correct)
- This change is preserved and committed
